# リフティングマスター

子供が毎日のリフティング最高回数を記録し、続けるほどキャラクターのレベルが上がって
進化する Web アプリ。記録はすべて端末の中だけに保存され、外部に送信されない。

**初めての方へ**: [`HANDOFF.md`](./HANDOFF.md) をお読みください。何のアプリか、動かし方、必須の設計、踏んだ罠（25件）、やり残しがまとめてあります。

設計書: `../docs/superpowers/specs/2026-07-26-lifting-app-design.md`
（**このリポジトリの外**にあるので、クローンした環境には無い。無くても `HANDOFF.md` だけで再開できる）

## つかいかた（開発）

```bash
npm test        # テストを実行（420件）
npm start       # http://localhost:8123/ で開く（ブラウザペイン有効）
npm run icon    # PWAアイコンを作り直す
```

npm install は不要（依存パッケージがゼロのため）。**Node.js v24.18.0 以上が必要**。

テストは `node --test test/*.test.js`（glob 展開）で実行する。`node --test test/`
（ディレクトリ指定）は Node 24 では `MODULE_NOT_FOUND` になるため使わないこと。
`test/helpers/` はテスト本体ではなく共有の道具置き場で、この glob には拾われない。

**開発環境**: `.claude/launch.json` により `npm start` でブラウザペインが立ち上がり、
実寸測定・スクリーンショット・クリックが可能（DOM検査・`getBoundingClientRect` で数値判定できる）。

## しくみ

- 記録の正本は `player.records` の配列だけ。レベル・自己ベスト・連続日数は
  そこから毎回計算する（保存しない）ため、表示と実データが食い違わない
- EXP は「その日・そのモードのベストを更新した差分」だけ入る。同じ数字を
  何度入れても増えない
- 計算ロジックは `js/core/` に純粋関数として置き、すべてテストがある。
  画面（`js/views/`）には計算を書かない
- `js/core/player.js` が、その純粋関数群と画面の間をつなぐ層になっている。
  記録の追加・承認・キャラ切り替えなど「プレイヤーの状態を1つ進める」操作は
  すべてここに集約されており、画面側は `js/core/exp.js` や `js/core/evolution.js`
  を直接組み合わせない

## ゲームバランスの調整

数値は `js/core/characters.js` に集めてある。ここを変えるだけで難易度が変わる。

- `MODE_RATE` — ノーバウンド／ワンバウンドの EXP 係数
- 各キャラの `evolutions` — 進化に必要なレベル・回数・連続日数
- 各キャラの `ability` — 特性（倍率のルールは `js/core/abilities.js`）
- `expToNext`（`js/core/exp.js`）— レベルアップに必要な EXP のカーブ
- `GAP_BREAK_DAYS`（`js/svg/chart.js`）— きろく帳の成長グラフで、何日空いたら
  線をつなげずに切るか（既定7日）。毎日はやらない子を想定した見た目の調整値

変更したらテストの期待値も直すこと（`test/exp.test.js` と `test/characters.test.js`）。

**特性の効き目:** 特性は Lv100 到達までの期間を **最大でおよそ 5 割** 縮める。
設計書には「最大3割」とあるが、これは実態と合っていない。もくも（ワンバウンドに
2倍）と こおる（ノーバウンド20回以上に2倍）は、条件を満たすかぎり担当モードの
EXP がそのまま2倍になるため、そのモードで遊び続ける子では所要期間がほぼ半分になる。
キャラ間の差を詰めたい場合は、この2体の倍率（`js/core/abilities.js` の
`fuwafuwa` と `reisei`）を下げるのがいちばん効く。

## 親の承認について

設定から ON にすると、子供の記録が「承認待ち」に入り、親がパスワードを入れて
確認するまで EXP が入らない。承認画面はパスワードで一度開いても、ホームに戻って
もう一度開くと再びパスワードを聞かれる（開いている間だけ有効な認証で、次に
入り直すときは保持されない）。

承認待ちの記録は、親の承認画面の「ぜんぶ みとめる」で一括承認できる。このとき
記録は必ず古い順に処理される。1件ずつ承認する場合は押した順に特性の倍率がかかるため、
自己ベスト・レベル・連続日数を見る特性のキャラでは順番によって合計 EXP が変わる
（仕様。`js/core/gain.js` のコメントと `test/player.test.js` の ひのこ のテストを参照）。

### 確定済み記録の修正・削除

子供が誤入力した場合、親のパスワードで以下の操作ができる：

- **修正**: きろく帳で日をタップして「なおす」ボタンを押し、回数を訂正する
  - 修正でレベルが下がる場合は事前に確認ダイアログが出る
  - 修正で新たに進化条件を満たした場合は、その場で進化演出が表示される
- **削除**: 同じく「けす」ボタンで記録を削除する
  - 削除しても二度と復帰しない（バックアップ JSON には残る）

親の承認 OFF 時は、修正・削除とも確認ダイアログだけでできる（パスワード不要）。

### この保護の強さについて

パスワードはハッシュ化して端末内に保存しているが、これは「子供が画面操作だけでは
突破できない」ことを目的とした割り切りである。ブラウザの開発者ツールを使える人間は
localStorage を直接書き換えられるため、**本格的な保護ではない**。大人が本気で
回避しようとすれば止められない。

画面操作の範囲でも、次の2点は知っておくこと。

- **子供は新しいプレイヤーを作れる。** せってい →「べつの ひとに かわる」→
  「あたらしく はじめる」で別のプレイヤーを作れてしまい、**新しいプレイヤーの
  承認は既定で OFF** なので、そちらでは承認なしに記録できる。承認 ON は
  プレイヤーごとの設定であり、端末全体のロックではない。
- **消す・置きかえる操作はパスワードで守られている。** 承認が ON のあいだは、
  「この プレイヤーを けす」と「よみこむ（バックアップの取り込み）」の実行前に
  パスワードを聞く。承認が OFF のときは確かめるパスワード自体が無いので、
  確認ダイアログだけで実行できる。

パスワードを忘れた場合は、設定時に登録した「あいことば」で解除できる。
両方忘れた場合は、バックアップ JSON を手で編集する以外に方法がない
（このため `js/storage.js` の検証は、手で書かれた JSON が来る前提で書いてある）。

## バックアップ

**記録は端末の localStorage にしかない。この端末以外のどこにも複製はなく、
ブラウザのデータを消す・端末を初期化する・別のタブレットに買い替えると記録は
消える。** 設定画面から JSON ファイルとして書き出せるので、ときどき保存して
おくこと。

読み込んだ JSON が壊れていたり検証に失敗した場合は、今のデータは変更せず
エラーだけを出す（詳しくは `js/storage.js` の `load`/`importJson`）。

## 配布

**公開URL: https://liftingmaster.github.io/**

2026-07-29 に `ryoichiabe-svg/lifting-master`（旧URL `https://ryoichiabe-svg.github.io/lifting-master/`）
から、Organization `liftingmaster` の `liftingmaster.github.io` へ移した。URL に個人名を
入れないためで、repo 名を `<Org名>.github.io` にしたのでパスなしのルートで配信される。
**旧URLは動かなくなる。** localStorage はオリジン単位なので、引っ越しの前に
「せってい → かきだす」でバックアップを取り、新URLで「よみこむ」で戻すこと
（この手順を踏まないと記録が消える）。ホーム画面のアイコンも追加し直しになる。

GitHub Pages（`main` ブランチのルート）で配信している。静的ファイルだけなので
ビルド工程はない。URL を渡せば他の子の端末でも使える（記録は各自の端末に保存され、
端末をまたいで共有されることはない）。

タブレットでは、この URL を開いてブラウザの「ホーム画面に追加」を選ぶと、
アイコンから全画面で起動するようになる。

### 更新するとき

```bash
# 1. sw.js の CACHE_NAME の版を上げる（v2 → v3 のように）
#    ※ 画像を追加したときは必ず上げること
# 2. コミットして push するだけ。1〜2分で反映される
git push
```

**`CACHE_NAME` を上げ忘れると、端末に残った古いキャッシュが配られ続けて変更が届かない。**
Service Worker はキャッシュ優先で動くため、これを忘れると「直したのに直らない」状態になる。

### やくそくは test/invariants.test.js に置く

この案件では「README やコメントに書いた約束が、あとで別のファイルで破られる」ことが
繰り返し起きた（`sw.js` への登録漏れ、`js/core` への DOM 混入など）。
人が思い出して守る仕組みは、担当が変わると効かない。

**約束を決めたら `test/invariants.test.js` に1本足すこと。** 現在9件あり、主なものは:

- 配信するファイルが全て `sw.js` の `ASSETS` に載っている（オフラインで壊れないこと）
- `sw.js` が実在しないファイルを指していない
- `js/core` が DOM・localStorage・時計に触れない
- `pendingUnlocks` の呼び出しが**すべて第3引数を渡している**（渡し忘れを3回やったので機械化した。
  違反は「ファイル:行番号」を名指しで落ちる）
- `CACHE_NAME` が過去の版へ戻っていない（**上げ忘れは検出できない**。下記のとおり手で確認する）

`npm test` で自動的に走るので、突合コマンドを手で叩く必要はもう無い。
ただし **`CACHE_NAME` の版上げは機械では判定できない**ので、これだけは手で確認すること。

## 配布まえの確認（キャッシュ対象の突合）

`sw.js` の `ASSETS` に載っていないファイルは、オフラインで読み込めずその画面が壊れる。
ファイルを増やしたときは、次のコマンドで漏れがないか突合すること。

```bash
node -e "const fs=require('fs');const sw=fs.readFileSync('sw.js','utf8');const listed=new Set([...sw.matchAll(/'\.\/([^']*)'/g)].map(m=>m[1]).filter(Boolean));const walk=(d,a=[])=>{for(const e of fs.readdirSync(d,{withFileTypes:true})){const p=d+'/'+e.name;if(e.isDirectory()){if(['node_modules','.git','.superpowers','.claude','incoming-art','test','tools','docs'].includes(e.name))continue;walk(p,a);}else a.push(p.replace('./',''));}return a;};const onDisk=walk('.').filter(f=>/\.(js|css|html|json|png)$/.test(f)&&f!=='package.json'&&f!=='sw.js');const missing=onDisk.filter(f=>!listed.has(f));console.log(missing.length?'漏れ: '+missing.join(', '):'漏れなし');"
```

あわせて `CACHE_NAME` の版を必ず上げること。上げないと古いキャッシュが配られ、
変更が端末に届かない。

### リポジトリの公開方針

2026-07-31 に、無料の GitHub Pages と単純な本番運用を維持するため、当面 public のまま
運用すると決定した。feature ブランチと Pull Request も公開される。秘密情報、認証情報、
子供の記録を書き出した JSON、個人情報は commit / push しない。記録は端末の
`localStorage` のみに保存する。

商品化、バックエンド・外部 API の導入、非公開の設計資料、複数人開発のいずれかが始まる
段階で、private な開発 repo への移行を再検討する。GitHub Free のまま現在の repo を private
にすると本番 Pages が停止するため、先に移行方法か契約変更を決めること。判断の詳細と禁止事項は
`HANDOFF.md` の「リポジトリの公開方針」を正本とする。

## キャラクターについて

9体すべてオリジナル。もともと全員 SVG をコードで生成していたが、現在 Task 28 で
生成画像への差し替えを進行中（**御三家3体・9枚が画像化完了**、残り6体は従来の SVG）。

### 現在の形態

- **御三家**（ひのこ・しずく・はっぱ）: 生成画像（`js/img/{hinoko,shizuku,happa}-{0,1,2}.png`）
- **その他6体**: コード生成 SVG（ぴかり・もくも・きらら・がんろ・こおる・かげろ）

画像があるかないかに関わらず `js/svg/character.js` の `characterSvg` が統一インタフェースで
返すため、呼び出し側は区別しない。どのキャラのどの形態に画像があるかは
`js/svg/artManifest.js` の `ART` オブジェクトに1か所で集約。

### 画像化の手順（御三家3体で確立済み）

残り6体を進める場合の手順。**以下はすべて実際に動かして確認した内容。**

1. **プロンプトを作る** — 1体につき3枚（初期・第1進化・第2進化）を別々に生成させる。
   ぴかりのプロンプトは `docs/art-prompts/pikari.md` にある。**これを雛形にして
   他のキャラぶんを書く。**背景を完全な透明にすること・輪郭線はキャラの色を暗くした色・
   おなかにクリーム色の面、が既存3体と揃えるための必須条件

2. **`incoming-art/` に置く** — フォルダを掘らずフラットに置く。ファイル名は
   `pikari-1.png`（初期）/ `pikari-2.png`（第1進化）/ `pikari-3.png`（第2進化）。
   **`-1/-2/-3` が stage `0/1/2` に対応する**（1つずれるので注意）。
   `incoming-art/` は gitignore

3. **変換する** — 出力先を1枚ずつ指定して実行する。
   ```bash
   node tools/prepare-art.js incoming-art/pikari-1.png js/img/pikari-0.png
   ```
   背景を透過にし、余白を整えて 512x512 の PNG を書き出す。
   **`incoming-art/` は自動では消えない**（元画像は残るので、必要なら手で消す）。
   元画像が最初から透過済みなら背景除去は自動で飛ばす（`transparencyProfile` が判定）

4. **目で見て確認する** — `node tools/make-art-preview.js` で
   `tools/art-preview-<キャラ>.html` を作り、ブラウザで開く（このHTMLは gitignore）。
   3段階が同じ大きさ・同じ重心に見えるか、縁に灰色のにじみが無いかを見る

5. **マニフェストに登録** — `js/svg/artManifest.js` の `ART` に1行足す
   ```js
   pikari: [0, 1, 2],
   ```

6. **キャッシュに追加** — `sw.js` の `ASSETS` に3ファイルを追加し、
   **`CACHE_NAME` の版を上げる**（忘れると端末に届かない）

7. **テストして push** — `node --test test/*.test.js` が全件通ればよい。
   `test/png-art.test.js` が 512x512・四隅の透明・透明率20〜90%・輪郭の灰色にじみを
   機械検査する。`test/invariants.test.js` は ASSETS の漏れと「**過去の版へ戻していないこと**」を見る。
   **現在の版から上げ忘れたことは機械では検出できない**ので、変更のたびに手で確認する
